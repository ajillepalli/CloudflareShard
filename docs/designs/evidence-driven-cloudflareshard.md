# CEO Plan: Evidence-Driven CloudflareShard

Generated by `/plan-ceo-review` on 2026-08-05
Branch: `main` | Mode: SCOPE EXPANSION
Repo: `ajillepalli/CloudflareShard`

## Vision

CloudflareShard becomes the adaptive, operator-owned SQL control plane for Cloudflare. A builder can deploy a real sharded workload in under ten minutes, understand why the system is making each recommendation, safely scale or recover it, and independently reproduce every performance and correctness claim.

The product remains self-hosted. CloudflareShard may collect evidence only through explicit, local-first export. Operators retain control of their data plane, administrative authority, and diagnostic artifacts.

### 10x Check

The 10x version is not a database library with more SQL features. It is a closed evidence loop:

```text
verified deployment
       |
       v
redacted workload evidence ---> capacity and risk explanations
       |                                  |
       v                                  v
production hardening <--------- safe operational plans
       |                                  |
       v                                  v
reproducible proof <----------- verified execution and rollback
```

Every consenting adopter can improve the evidence used to prioritize hardening. Every operational feature emits proof that can be replayed in regression and fault tests. Every public claim is reproducible under a declared environment.

### Platonic Ideal

The operator experience feels calm and legible:

- The first successful workload is verified, not merely deployed.
- Topology, transaction health, cost, capacity, and recovery posture are visible in one place.
- Automation explains its evidence and uncertainty before requesting authority.
- Destructive changes are previewed, audited, and invariant-checked; each is either reversible within a declared window or explicitly marked irreversible and protected by a verified restore point.
- The system can honestly recommend that a workload remain on D1 or unsharded SQLite.
- Correctness and performance reports disclose configuration, failures, cost, and statistical uncertainty.
- A new engineer can reconstruct an incident or release decision from durable evidence rather than tribal knowledge.

## Chosen Implementation Approach

The approved sequence is A, then B, then C, with a short acquisition gate A0 before material new infrastructure. Each phase has an evidence gate; calendar completion alone does not unlock the next phase.

### Phase A0: Acquisition Proof

Goal: prove that the wedge reaches at least one qualified builder before funding speculative control-plane depth.

Exit criteria:

1. Correct the Free/Paid documentation and make one clean-account golden-path run reproducible from the public README.
2. Publish one small, explicitly preliminary benchmark using a bespoke CloudflareShard OLTP workload, neutral names, and neutral metrics. Report failures, timeouts, configuration, seed, environment, and deviations, and make no production-capacity claim. Keep the existing TPC-derived harness private unless written TPC permission is obtained.
3. Build a named prospect list and complete at least ten problem interviews from at least thirty targeted contacts within four weeks.
4. Secure at least one qualified design partner with an existing workload, a stated sharding or transaction pain, a named technical owner, and an agreed measurable test.

If no qualified partner emerges after that bounded outreach, pause Phase B/C infrastructure work, revise the wedge and positioning, and repeat A0. Stars, page views, and deploy clicks do not override this stop condition.

### Phase A: Adoption and Validation

Goal: prove that qualified builders can reach recurring value and produce actionable workload evidence.

Exit criteria:

1. Across at least twenty clean-account trials, p90 time from authenticated Wrangler session to verified workload is under ten minutes on the supported Free-plan path; account creation and DNS are measured separately.
2. Three to five qualified design partners are onboarded, where qualification requires an existing workload, a stated scaling or transaction pain, a named technical owner, and agreement on a measurable success test.
3. At least three partners complete deployment and at least two run three or more repeated workloads in isolated, disposable, or shadow environments for at least seven days; this cohort supports discovery only, not generalized production claims.
4. Activation is measured as `deploy -> first successful workload -> repeated workload`; stars and deploy clicks remain acquisition signals only.
5. The opt-in Evidence Recorder produces a redacted, inspectable bundle without query contents or tenant identifiers.
6. Onboarding friction and workload findings are recorded in one decision log that can change Phase B priorities.

Phase A safety floor:

- Minimal transaction invariants run on every release: at-most-once request application plus durable result replay within the declared idempotency window, all-or-none 2PC outcome, no stale-route write after cutover, and source/target equality after reshard.
- Coordinator restart, response loss after commit, and hot-shard overload fault cases run before partner onboarding.
- Partner workloads remain isolated, disposable, or shadowed unless a documented recovery path and explicit data-loss budget exist.
- Recommendations are labeled workload-specific and cannot mutate topology.

### Phase B: Production-Ready v3

Goal: harden the failure and operating surfaces demonstrated by Phase A evidence.

Baseline production work:

- Durable cross-shard transaction recovery and continuously checkpointed progress; the existing one-per-transaction CoordinatorDO becomes the canonical 35-day redo envelope, and a sharded commit-manifest index outside the participant restore set makes decisions enumerable
- Overload detection, backpressure, and explicit handling of Durable Object overload errors
- Fleet-aware PITR preparation, restore orchestration, and restore-rehearsal runbooks
- Versioned, backward-compatible schema rollout with explicit rollback constraints
- Idempotent alarms and durable scheduling state
- Per-object and fleet SLO telemetry with export for retention beyond native log windows
- Capacity thresholds grounded in observed workloads
- Unique-index work only when an adopter supplies a concrete cross-shard uniqueness requirement

Phase B is split into four evidence gates:

1. **B1, foundational reliability:** transaction recovery, overload handling, schema compatibility, idempotent alarms, restore contracts, and minimum SLO telemetry.
2. **B2, operator visibility:** read-only Shardscope fleet view, evidence-backed diagnostics, audit history, and restore rehearsals.
3. **B3, guarded operations:** approved console mutations and offline Autopilot recommendations.
4. **B4, optional mutating automation:** one narrowly bounded automatic action only after B1/B2 are production-ready and observed demand independently justifies automation; B4 cannot delay the production-readiness release.

Expanded product work:

- Shardscope as the authenticated production operator console
- Reversible Shard Autopilot with a multi-action planner for split, migrate, drain, and rebalance; learning is shared, while guarded execution authority is promoted and revoked independently per action type
- Offline Shard Advisor CLI report; import automation requires at least three successful manual migrations with the same recurring failure pattern, and online cutover remains a separate evidence-gated milestone

### Phase C: Benchmark and Correctness Moat

Goal: publish reproducible evidence after the production behaviors being claimed are implemented and verified.

Required lanes:

- Quick CI and release-regression workload lane
- Publishable steady-state performance lane with repetitions and uncertainty
- Separate correctness and fault-injection lane
- Six-region, architecture-matched D1 comparisons using fixed external clients in US West, US East, Western Europe, East Asia, Southeast Asia, and Australia, plus controlled mixed-region runs
- Cost per successful business operation
- Reshard impact and rollback measurements
- Sanitized workload replay from design-partner evidence

The minimal correctness and fault harness begins in Phase A and expands during Phase B. Phase C adds at least 120 minutes after steady state for the TPC-derived lane, repetitions, comparison methodology, and independent reproducibility; any other lane uses a workload-specific preregistered minimum duration. It does not postpone basic correctness testing.

Publication prerequisite: do not publish or publicly name TPC-derived work without written TPC permission. If permission is obtained for a later Phase C lane, use the required `Derived from` naming and disclaimer, retain required notices, disclose every deviation and environment, omit protected metrics, never compare with official results, and never imply compliance. Otherwise Phase C uses only bespoke workloads and neutral metrics.

## Operational Definitions

- **Verified deployment:** bindings resolve, catalog and shard health checks pass, one single-shard and one cross-shard transaction persist, restart recovery preserves acknowledged writes, and the topology view reports the expected placement.
- **Successful business operation:** the declared logical operation completes its required invariant, excluding retries, setup calls, and partial or timed-out attempts.
- **Continuously checkpointed:** every externally visible transaction-state transition is durably recorded before acknowledgement; in-memory state is never required for recovery.
- **Fleet-aware:** an operation enumerates the catalog-defined shard/coordinator set, records omissions, and never treats a partial response as complete.
- **Architecture-matched comparison:** the compared systems receive equivalent logical operations, transaction semantics, client regions, datasets, offered load, warm/cold policy, and failure accounting; architectural differences remain disclosed.
- **Recommendation precision:** among recommendations whose outcomes are observable, the percentage that avoid a false-positive topology action under the pre-registered safety criterion.
- **Production-like workload:** a sanitized operation mix, key distribution, concurrency, and duration derived from a real application and run outside its authoritative production data path.

- **CLI:** deployment, preflight, verified activation, offline support bundles, and Advisor reports.
- **Evidence Recorder:** bounded per-DO aggregates/outboxes drained by alarms into deterministic EvidencePartitionDOs; an epoch-aware EvidenceManifestDO owns schema, partition-map, coverage, and export metadata. Correctness, recovery, and privileged-operation records are durable, optional workload samples may shed with explicit coverage counters, and no remote transmission path is enabled by default.
- Evidence outboxes reserve a mandatory audit lane. Optional workload samples compact or drop with explicit counters; exhaustion of mandatory capacity rejects privileged mutations with `507 AUDIT_CAPACITY_EXHAUSTED` before lease acquisition or state change, without blocking ordinary application traffic.
- **Shardscope:** read-only operational truth in B2; mutation requests use explicit authorization, operation leases, previews, and audit records in B3.
- **Autopilot:** policy evaluation separated from execution; it cannot bypass Shardscope/CLI authorization or catalog operation leases.
- **Advisor:** offline fit and migration analysis from declared schema plus privacy-safe operation templates.
- **Proof Lab:** testing and report generation; it cannot make production mutations outside an explicitly provisioned test target.
- **CoordinatorDO:** canonical immutable cross-shard redo envelope, durable decision state, and reconciliation. One object already exists per transaction; v3 adds `commit_decided_at`, retention state, and a decision hash, and moves the durable decision before participant commit propagation.
- **JournalManifestDO:** deterministically sharded, time-bucketed index of committed transaction IDs, decision times, coordinator IDs, and hashes. Registration is acknowledged before participant commit and the namespace is excluded from participant PITR restores, allowing complete cutoff enumeration without copying full payloads onto the request path.
- **JournalArchiveWorker:** optional route-less service-binding boundary that holds archive master keys and R2 access. It asynchronously seals manifest batches plus referenced envelopes into encrypted R2 segments; archive lag is observable but cannot block or change transaction correctness.
- **CatalogDO:** topology epochs and shard membership; it validates lease fencing tokens but is not the lease authority.
- **TopologyLeaseDO:** per-fleet hierarchical leases over catalog, shard, vBucket, and index-ring resources; it serializes atomic acquisition decisions but not the lifetime of disjoint operations.
- **ControlPlaneWorker:** separate route-less/service-bound deployment using declarative `exports` from inception; owns TopologyLeaseDO, EvidencePartitionDO, EvidenceManifestDO, JournalManifestDO, and Autopilot policy state while existing core namespaces remain on legacy migrations.

## Correctness and Recovery Contracts

1. An acknowledged write survives object restart within the guarantees of Durable Object storage.
2. A request ID is applied at most once within a deployment-configured 1-30 day idempotency-retention window, defaulting to seven days. Responses, SDK diagnostics, and support bundles expose the effective expiry; automated retries stop before that deadline. Reuse after expiry is treated as a new request and documented as unsafe for replay.
3. A committed cross-shard transaction is all-or-none after reconciliation; intermediate prepared state is not presented as committed.
4. The coordinator persists its decision before participants are told to commit and uses fenced transaction epochs to reject stale recovery actors.
5. Poison transactions enter a visible typed quarantine after bounded retry. Preparing/prepared work may abort only under a fenced recovery lease before a durable commit decision. Committed work may only reconcile or execute an idempotent generated repair that lists participant effects, invariant checks, and rollback limits; the decision can never change to abort. Every action requires re-authentication and an append-only audit record.
6. Resharding prevents stale-epoch writes after cutover, checkpoints backfill progress, verifies source/target equality, and declares its rollback deadline and required headroom before execution.
7. Fleet restore is not claimed to be an atomic cross-object snapshot. The supported contract is restore-to-bookmarks followed by transaction-log reconciliation within a declared RPO/RTO; any unreconciled interval is reported explicitly.
8. Ordinary object restart has RPO 0 for acknowledged writes within the provider storage guarantee. An operator-selected PITR intentionally discards writes after its declared cutoff and reports that data-loss window before execution. Topology/configuration exports target RPO <= 5 minutes. A rehearsed reference fleet of 8 shards targets RTO <= 30 minutes; larger fleets publish measured RTO rather than inheriting that target.
9. Fleet PITR selects one logical cutoff `T`. Recovery replays only cross-shard decisions durably committed at or before `T`, and only when a participant bookmark predates that transaction's prepared mutation. Transactions decided after `T` are never replayed; single-shard and cross-shard work after `T` is consistently discarded and enumerated in the restore report.

### Transaction decision journal

- CoordinatorDO is the canonical journal. Before any participant receives `commit`, it atomically persists an immutable, versioned redo envelope, decision epoch, `commit_decided_at`, participant set, operation hash, and retention deadline. A decision-only witness is insufficient: the envelope must reconstruct every participant mutation when PITR predates prepare.
- The coordinator then synchronously registers `{fleet, time_bucket, tx_id, coordinator_id, commit_decided_at, decision_epoch, envelope_hash}` in a deterministic JournalManifestDO partition. Registration is idempotent and content-addressed. Failure or ambiguity blocks participant commit propagation but cannot reverse the already durable commit decision.
- Only after both local decision persistence and manifest acknowledgment does the coordinator propagate commit. A crash at any earlier boundary resumes registration; a crash after acknowledgment resumes participant reconciliation.
- CoordinatorDO and JournalManifestDO records are retained for at least 35 days and are never included in a participant fleet PITR operation. Lifecycle deletion is alarm-driven, idempotent, and allowed only after the retention deadline and archive policy checks.
- Restore enumeration scans sealed time buckets covering cutoff `T`, verifies manifest/envelope hashes, and opens the referenced CoordinatorDO envelopes. Missing buckets, hash conflicts, or gaps create a visible manual-repair case and block a successful restore declaration.
- Participants persist their observed decision and topology epoch. Recovery chooses the monotonic safe outcome: a valid commit witness or committed participant can never be converted to abort.
- Each coordinator maintains a manifest-admission circuit breaker. Three registration failures within 30 seconds open the circuit before prepare; recovery work has priority, half-open state permits one bounded manifest probe, and cooldown backs off to five minutes. Rejected clients receive `503 JOURNAL_UNAVAILABLE` with retry guidance.
- An ambiguous manifest acknowledgment enters `commit_pending_manifest`, returns `202 Accepted` with polling, retains prepared participant state, and retries the identical registration. Existing content with a different hash triggers quarantine rather than overwrite.
- Optional encrypted R2 segments are produced asynchronously from sealed manifest buckets. They are useful for offline audit and retention beyond 35 days, but R2 availability, lag, decryption, or deletion never changes the primary PITR recovery contract.
- The engineering review must benchmark JournalManifestDO partitioning and choose a shard/time-bucket function that stays below measured per-object saturation; no singleton journal object is permitted.

### Online reshard data path

1. Source remains authoritative while a checkpointed snapshot backfills the target.
2. Source writes append to an ordered migration change log keyed by topology epoch; the target replays it idempotently.
3. Cutover requires source/target checksum agreement, measured convergence, a fresh restore point, and capacity headroom computed from observed dataset size, write rate, catch-up rate, and temporary-copy overhead. Initial qualification targets are change-log lag below one second and 2x migrating-data capacity plus 20% working headroom; they are not promises until workload evidence validates them.
4. A catalog lease briefly quiesces writes, advances the topology epoch, drains the final log, and fences stale writers. Two seconds is the initial measured target, not a fixed guarantee; preview reports the workload-specific bound and aborts before cutover if it cannot be met.
5. A reverse change log is retained for a previewed rollback window derived from write rate, available capacity, and operator policy. Thirty minutes is the initial qualification target. After expiry, rollback requires a new migration or restore and is labeled irreversible in the approval plan.
6. Migration aborts before cutover if headroom falls below the requirement, the log cannot converge, or elapsed time exceeds 24 hours; the source remains authoritative.

During the rollback window, every acknowledged target write first appends idempotently to the durable reverse log. Rollback replays that log to the source, requires measured convergence plus source/target checksum agreement, briefly fences writes under the catalog lease, advances the topology epoch back to the source, and rejects stale target writers. Failure to converge before the previewed window expires disables rollback and requires a new forward migration or restore.

## Security and Evidence-Sharing Contract

- Console roles start with `viewer`, `operator`, and `admin`; mutation, policy promotion, restore, and credential management are separate audited permissions.
- Human authentication uses a cryptographically validated Cloudflare Access JWT; header presence alone is never trusted. Automation uses scoped Access service identities. Authorization remains a CloudflareShard decision mapped to local account/fleet roles rather than inferred solely from identity-provider membership.
- Access JWKS keys are cached by `kid`. A previously verified known key may be used for at most one hour beyond normal cache lifetime during refresh failure and records `jwks_stale=true`; unknown keys return `503 AUTH_KEY_UNAVAILABLE`, and restore, break-glass, policy promotion, and irreversible actions require fresh JWKS.
- Every identity is scoped to an account and explicit fleet set; object IDs alone never grant access across fleets.
- Sessions expire after 30 minutes of inactivity and 12 hours absolute. Restore, policy promotion, credential changes, and irreversible operations require re-authentication within five minutes and CSRF-protected requests.
- Audit records are append-only, integrity-chained, exported for at least one year, and include actor, fleet, request ID, evidence hash, decision, and result.
- Break-glass uses offline Ed25519 recovery keys whose public keys are registered at setup. Solo fleets may require 1-of-1 and team fleets 2-of-N distinct signatures. Activation names a reason, fleet, and capability set; resulting recovery-only sessions expire after 15 minutes and create immediate audit/notification events.
- Administrative credentials remain in Cloudflare secrets or supported local credential stores, are never embedded in evidence bundles, and have documented rotation procedures.
- Optional R2 archive segments use AES-GCM with fleet ID, time bucket, manifest epoch, and segment hash as authenticated metadata. Each fleet has a random data-encryption key wrapped by a versioned user-managed master key stored as a Worker secret. Old master-key versions remain until all protected archives expire and an archive-open rehearsal passes. Loss of archive keys affects only optional long-term/offline recovery evidence, not the canonical 35-day CoordinatorDO recovery contract.
- Evidence uses an application-declared semantic operation registry: stable versioned operation IDs, normalized templates, synthetic parameter generators, timing/dependency traces, and aggregate key-distribution statistics. Local Advisor analysis may inspect the real schema, but shared bundles contain aliases. Raw query text, literal values, tenant IDs, tokens, and headers are denied by schema.
- Bundle creation runs secret-pattern and high-cardinality scans, displays the complete manifest, and requires explicit operator approval before export.
- Bundle export seals against a manifest epoch and is complete only when every assigned partition responds. Operators may explicitly request a partial diagnostic artifact after a bounded wait, but its manifest lists missing partitions/time ranges/drop counters and machine-blocks benchmark publication and Autopilot promotion.
- Bundles are signed for provenance and always encrypted to a named recipient for external export. The project defines recipient, purpose, retention deadline, and deletion request in the bundle manifest. CloudflareShard provides no built-in remote upload destination; the operator transfers the offline artifact through their chosen channel.
- Consent can be withdrawn for remotely shared artifacts; the project records deletion completion, while already published aggregate results remain governed by their original disclosure agreement.
- Re-identification and secret-leakage tests gate the first bundle schema and every schema version.
- Imported operation registries and evidence bundles remain untrusted even when signed. Templates are declarative only: bounded enums, ranges, size classes, distributions, and dependency references; scripts, SQL, shell commands, URLs, filesystem paths, and arbitrary expressions are rejected. Replay targets are disposable and resource-capped, and imported evidence cannot authorize Autopilot execution.

Evidence lifecycle:

```text
record locally -> schema denylist -> redact/synthesize -> scan -> operator inspect
      -> approve named purpose/recipient/retention -> sign/encrypt -> share
      -> ingest to decision log -> expire/delete -> record deletion outcome
```

## Upgrade and Compatibility Contract

- CI pins and tests a declared Wrangler, Workers compatibility date, SDK, and CloudflareShard version matrix.
- Coordinator, catalog, shard, CLI, and console protocols carry explicit versions; unknown newer write formats fail closed.
- Schema changes are expand-first and backward-readable across one supported release window.
- Rollout order is catalog/coordinator readers, shard readers, writers, then clients; rollback is allowed only while stored data remains readable by the prior version.
- Mixed-version and interrupted-rollout tests are required before a release changes durable state.
- Durable Object lifecycle changes and storage-backend changes are called out as non-code-rollback boundaries with separate migration and restore procedures.

## Operational Failure Requirements

The build plan must include named behavior and tests for Cloudflare API failure/rate limiting, account quota exhaustion, shard unavailability, coordinator restart, catalog unavailability, concurrent reshard/schema/restore requests, stale recommendations, interrupted restore, insufficient rollback capacity, expired credentials, storage-full writes, late/duplicate alarms, and partial fleet enumeration.

Fleet-mutating operations acquire a catalog lease and topology epoch. Conflicting operations fail visibly before mutation. Every plan checks rollback headroom and restore-point freshness before approval.
Every privileged mutation uses an immutable preview containing a plan ID, parameter hash, topology epoch, resource set, impact, expiry, and rollback contract. Execution revalidates the preview and creates one resumable operation under a stable idempotency key; stale or mismatched approvals return 409 without mutation.
Lease loss moves an operation to `parked_lease_lost` and stops mutation. Only an explicit resume of the same operation ID may reacquire its hierarchical resources, after topology epoch, authority, checkpoint, rollback headroom, and restore-point invariants pass; irreversible boundaries recheck the lease immediately before mutation.

## Cost and Capacity Contract

- Every estimate records the Cloudflare pricing-document version/date, plan, region assumptions, workload-evidence version, topology, and calculator version.
- Inputs include successful operations, retries, row reads/writes, DO invocations, GB-s, storage, transaction participants, skew, and growth rate.
- Outputs are ranges with confidence and sensitivity, never a single guaranteed bill or capacity number.
- Estimates older than 30 days or built from incomplete evidence display `stale`/`insufficient evidence` and cannot authorize Autopilot mutation.
- Before B3, estimates must fall within +/-20% of measured cost and saturation onset on at least five held-out trials spanning three workload shapes; otherwise the console shows measurements only.
- Paid-plan operation-cost models must separately show canonical CoordinatorDO writes, JournalManifestDO registration, participant calls, storage, and compute. Back-of-envelope architecture comparison, explicitly outside the product estimate contract: at a sustained 100 cross-shard transactions/second for a 30-day month, one additional SQLite row per transaction is 259.2 million logical rows/month and roughly $209-$211 beyond the June 2026 included allowance before index amplification, compute, or storage; one Standard R2 PUT per transaction is $1,165.50 after the one-million-operation free tier and million-operation rounding, before reads/storage. Refresh both against current official pricing and measured row amplification before implementation.
- The Free-plan golden path is a bounded evaluation path, not an implied high-throughput production allowance. Doctor reports daily row-write headroom and fails the sample early with a clear upgrade/teardown message rather than discovering quota exhaustion mid-workload.
- Before any M-or-larger work package starts, the maintainer records available person-weeks, maximum concurrent workstreams, and the package explicitly displaced. If no capacity declaration exists, assume one active implementation workstream and finish A0/A1 before starting B infrastructure.

## Benchmark Publication Contract

- Pre-register workload definitions, schema, dataset, topology, regions, runtime versions, warm-up, offered load, duration, repetitions, failure accounting, and statistical methods.

## Reviewer Concerns

The CEO plan completed the maximum three independent spec-review rounds and reached 9/10. The final reviewer verified consistency and scope discipline, while leaving these implementation risks for explicit ADR validation:

3. **Rollback correctness:** fault-test target-side reverse-log durability, catch-up, checksum, write fencing, and rollback-window expiry across all named interleavings.

## Section 7 Resolution: Performance Budgets

- Preserve the existing maximum of eight distinct transaction participant keys until evidence supports change.
- Define a maximum serialized recovery envelope and reject oversized transactions before prepare; set the initial limit from measured current worst-case payload plus headroom in the engineering review rather than guessing here.
- At 80% saturation, durable decision plus manifest registration may consume at most 20% of cross-shard transaction p95. Missing the budget blocks the production gate; it never authorizes skipping either durability step.
- Evidence recording performs no cross-object call on the request path. Local aggregate/outbox work has a measured CPU/storage budget and optional sampling sheds before application SLOs fail.
- Bundle export and Proof Lab reports stream/paginate partition data; no fleet-wide artifact is accumulated unbounded in Worker memory.
- Autopilot simulations and Advisor analysis have explicit input, CPU, memory, and result-size caps.

## Section 9 Resolution: Deployment and Rollout

Lifecycle choice:

- Existing core Worker keeps legacy `[[migrations]]`; existing CatalogDO, ShardDO, and CoordinatorDO namespaces are not transitioned to `exports` during v3.
- New `ControlPlaneWorker` uses declarative `exports` from its first deployment for TopologyLeaseDO, EvidencePartitionDO, EvidenceManifestDO, and JournalManifestDO.
- `JournalArchiveWorker` is an optional separate route-less Worker with R2/key bindings and no Durable Object lifecycle.
- Lifecycle changes never share a deploy with enabling a user-visible mutation feature.

Deployment sequence:

```text
1. deploy ControlPlaneWorker namespaces, including JournalManifestDO, via exports (dark)
2. run service-binding, manifest partition/sealing, retention, and DO smoke tests
3. deploy core CoordinatorDO schema readers/writers with the new path disabled
4. enable redo-envelope and manifest shadow verification in staging
5. enable the pre-participant decision/manifest contract for a canary fleet
6. optionally deploy R2 bucket policy + JournalArchiveWorker and verify archive lag/opening without making it a commit dependency
7. deploy read-only Shardscope production views
8. enable previewed operator mutations per fleet
9. enable Autopilot recommendations per action
10. promote individual Autopilot executors only after their gates pass
```

Feature flags are per fleet and monotonic in authority: read -> preview -> manual execute -> recommend -> automatic execute. A higher level cannot enable unless every lower gate passes.

Rollback flow:

```text
incident
  |
  +--> disable affected feature/authority flag
  |
  +--> stop new privileged or cross-shard admission if safety uncertain
  |
  +--> preserve coordinator redo, manifest namespaces, and any R2 archives
  |
  +--> reconcile in-flight operations under current durable contracts
  |
  +--> roll back code only when stored/protocol versions remain N-1 readable
  |
  +--> otherwise deploy a forward fix and run restore/invariant verification
```

First five minutes: validate bindings, Access JWTs, service identities, health probes, manifest circuit state, namespace reconciliation, schema versions, and one disposable single/cross-shard transaction. First hour: watch decision/manifest latency and failures, recovery age, optional archive lag, evidence lag/loss, lease conflicts, audit completeness, and canary SLOs. Rollout halts automatically on invariant failure, unknown durable-state version, manifest gap, audit gap, or recovery age above the gate.

## Section 10 Resolution: Long-Term Trajectory

Reversibility: **3/5**. Feature authority and the optional archive Worker are reversible, but CoordinatorDO decision semantics, new manifest/control-plane Durable Object namespaces, and stored protocol versions create durable path dependency.

- Support current and N-1 protocol/schema versions for one documented release window; reject unknown newer write formats.
- Every state machine and durable schema has an ADR, transition diagram, compatibility table, and runbook before implementation.
- Keep coordinator redo, commit manifests, optional R2 archives, control-plane lifecycle, and application data in explicit restore and permission boundaries.
- Do not add generic SQL breadth without adopter evidence; production credibility comes from recovery, control, and proof.
- B1/B2 constitute the production-ready release. B3 recommendations and B4 mutation are independently cancellable platform layers.

### Transaction and manifest state machine

```text
NEW
  -> preparing(epoch E)
       -> abort_decided(E) -> aborting(E) -> aborted(E)
       -> prepared(E)
            -> commit_decided(E) + durable forward work
                 -> commit_pending_manifest(E)
                      -> manifest_registered(E)
                           -> committing(E)
                                -> committed_pending_ack(E)
                                     -> committed(E)

Any valid state plus mismatched envelope/hash/epoch -> quarantined
Any state at or after commit_decided may only move forward or quarantine.
No state at or after commit_decided may abort.
```

Durable/effect ordering:

```text
validate immutable envelope and byte limit
  -> persist preparing(E) and participant set
  -> prepare every participant with E
  -> compare-and-set prepared(E)
  -> pre-arm recovery alarm
  -> atomically persist commit_decided(E) plus forward-work row
  -> register identical content-addressed manifest record
  -> persist manifest_registered(E)
  -> send participant commits with E
  -> persist acknowledgments and terminal committed(E)
```

An ambiguous manifest acknowledgment returns `202 commit_pending_manifest` with a pollable transaction ID. An ambiguous participant acknowledgment returns `committed_pending_ack`. Explicit state dispatch prevents `/begin`, alarms, shard sweeps, and `/force-abort` from falling through to the wrong phase. Participant tombstones retain the highest decision epoch long enough to reject late messages throughout the coordinator retention window.

### Performance review

1. Measure the serialized redo envelope before implementation and reject oversize work before prepare with `413 TX_ENVELOPE_TOO_LARGE`. The initial qualification target is at most 256 KiB per transaction and at most eight participant keys; the measured result may lower this ceiling but may not raise it without a new review.
2. Route manifests by UTC day plus `sha256(tx_id) mod 16`, with the partition count encoded in the protocol version. This avoids a singleton while bounding A-phase enumeration. Re-benchmark and version any partition change before B1 scale claims.
3. A transaction adds one synchronous manifest registration before participant commit. Qualification budgets are p95 manifest registration overhead <=100 ms on the reference deployment and no more than one registration RPC per original transaction plus explicit idempotent retries after ambiguity.
4. The benchmark driver is closed-loop preliminary evidence, not saturation or production-capacity evidence. It records timeouts and late completions, uses actual elapsed duration, and never drops failed attempts from denominators.
5. `doctor -> deploy -> seed -> verify -> receipt` retains the A1 p90 under-ten-minute gate across 20 fresh trials. Each step records its own duration so the dominant blocker is visible.
6. Recovery traffic has priority over new prepare admission. A manifest overload opens the admission circuit before prepare; Cloudflare overload errors are not hot-loop retried, and alarms use bounded backoff plus durable rescheduling.


### Error flow

```text
request
  -> validate/authenticate/authorize
      | fail -> typed 4xx/503 + remediation + audit when privileged
      v
  -> admission/capacity/lease checks
      | fail -> typed 409/429/503/507, no mutation
      v
  -> durable local transition
      | fail -> 5xx/507, no external effects
      v
  -> required cross-object acknowledgment
      | unknown -> durable pending state + 202/poll + alarm retry
      | conflict -> quarantine + operator repair workflow
      v
  -> external effects/reconciliation
      | partial -> committed_pending_ack + retry, decision unchanged
      v
  -> verify invariant + success receipt
```

### Restore data flow

```text
operator chooses cutoff T
  -> immutable preview lists affected ShardDOs and intentional loss window
  -> restore participant bookmarks only
  -> enumerate sealed JournalManifestDO buckets through T
  -> open CoordinatorDO redo envelopes with decision <= T
  -> repair only participants whose bookmark predates prepare
  -> verify checksums/invariants and enumerate every discarded post-T write
  -> complete with measured RPO/RTO OR remain manual_repair_required
```
